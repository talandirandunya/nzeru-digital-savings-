ABSTRACT

Many individuals and small-scale earners face persistent challenges in managing savings consistently, tracking deposits transparently, and accessing structured micro-credit services. Informal saving practices often lack accountability, planning support, secure records, and decision-making tools. This project, Digital Saving Vault (Nzelu Digital Savings), was developed to provide a modern digital platform for savings plan creation, deposit and withdrawal management, credit eligibility assessment, loan repayment tracking, financial reporting, and personalized account settings.

The system uses a Flutter frontend for cross-platform user access and a Django REST Framework backend for secure data processing and API delivery. The application supports user authentication, profile management, normal and secret savings plans, trial savings plans, deposit history, penalties for missed commitments, financial score calculation, and a credit system linked to tracked savings. In the implemented credit model, eligible users can request loans based on a percentage of their tracked savings, while repayments update loan balances and may generate interest rewards back into savings.

The platform also provides dashboard analytics, recent transaction summaries, notifications, settings management, and report generation to improve financial visibility. Local persistence and responsive user interfaces enhance usability, while backend validation enforces business rules such as credit limits, balance recalculation, and withdrawal restrictions when active credit exists.

This project demonstrates how software engineering, mobile development, API-based architecture, and financial workflow automation can be combined to improve savings discipline, transparency, credit access, and user confidence in digital microfinance systems.

Keywords: Digital Savings, Microfinance, Flutter, Django REST Framework, Credit Management, Financial Reporting, Notifications, Transaction Tracking

CHAPTER I

INTRODUCTION

1.1 INTRODUCTION

Saving money consistently remains a challenge for many individuals, especially where income is irregular, financial planning tools are limited, and informal methods of storing money are still common. Traditional saving practices often depend on manual records, memory, or unstructured group arrangements, which can expose users to poor tracking, low financial discipline, delayed decision-making, and limited access to structured credit services.

With the growth of mobile technology and digital financial services, there is increasing demand for applications that allow users to save securely, monitor transactions in real time, track financial goals, and access controlled micro-credit based on their saving behavior. Digital financial platforms can improve accountability, support planning, and provide visibility into savings progress, obligations, and repayment patterns.

Digital Saving Vault (Nzelu Digital Savings) was developed to address these needs by providing a centralized digital platform for account access, savings plan creation, savings deposits, withdrawals, penalties, reports, and credit management. The application combines a Flutter-based client with a Django REST backend to support modern financial workflows using an API-driven architecture.

The system includes multiple savings plan types, secret savings support, trial savings plans, transaction history, financial score calculation, credit eligibility assessment, repayment tracking, user notifications, and configurable settings. Through these features, the project aims to help users build saving discipline, improve transparency, and access structured credit in a secure and understandable way.

1.2 OBJECTIVES

The primary objectives of this project are:

  1. To design and develop a cross-platform digital savings application for users to create and manage structured savings plans.
  2. To provide secure user authentication, profile management, and personalized account settings.
  3. To implement deposit, withdrawal, and transaction tracking features for transparent financial record management.
  4. To support secret savings and trial savings plans for flexible user saving behavior.
  5. To develop a credit eligibility and loan management module linked to tracked savings performance.
  6. To automate loan repayment tracking and reward distribution after successful repayment.
  7. To provide dashboard analytics, financial summaries, and reports for improved decision-making.
  8. To build a notification system for reminders, alerts, and user engagement.
  9. To evaluate the platform as a digital microfinance support tool for savings discipline and controlled credit access.

1.3 SIGNIFICANCE OF THE STUDY

The significance of this study lies in its contribution to digital financial management at an individual and small-group level. Many users in low-resource and emerging digital finance environments do not have access to a dedicated platform that combines savings planning, financial behavior tracking, controlled credit access, and personalized reporting in one unified system. This project addresses that gap by proposing and implementing a platform that is not only technically functional but also behaviorally supportive.

From a practical perspective, the project contributes to improved savings culture by encouraging scheduled saving, goal tracking, and visibility into account progress. It also demonstrates how software engineering can be applied to solve financial organization problems faced by students, workers, traders, and small business owners who may not use formal financial planning tools regularly.

From an academic perspective, the project demonstrates the integration of cross-platform mobile development, backend API design, relational data modeling, financial business logic, and reporting in one system. It therefore serves as a meaningful case study in full-stack application development for computer science education.

1.4 SCOPE OF THE PROJECT

The scope of Digital Saving Vault includes user registration, login, profile management, savings plan creation, deposit and withdrawal recording, penalty handling, loan eligibility checking, loan request submission, loan repayment tracking, dashboard analytics, notifications, user settings, and financial reporting. The project focuses on the software structure and digital workflows needed to support these features.

The scope does not yet include live payment gateway settlement, real banking integration, production-scale loan approval workflows by external officers, legal compliance certification, or national identity verification. Those features are reserved for future expansion phases.

2.2.1 GAP ANALYSIS

The reviewed systems and technical sources reveal several gaps that justify the need for this project. First, many basic savings applications provide only balance storage and simple transaction logs, without structured plan management, flexible frequencies, or penalty rules to support saving discipline. Second, some platforms support savings but do not connect savings behavior to responsible credit access, which limits their usefulness in microfinance settings.

Third, many solutions do not offer integrated dashboards, secret savings categories, trial plans, repayment tracking, and user-level financial scoring in one platform. Finally, there is often inadequate support for personalized settings, role-aware data handling, and consistent synchronization between mobile interfaces and backend financial rules. Digital Saving Vault addresses these gaps through integrated savings, transaction, credit, reporting, and notification modules.

2.3 PROBLEM DEFINITION

Users who want to save consistently and access small-scale digital credit often face challenges such as poor record keeping, lack of transparent plan tracking, weak financial discipline mechanisms, and limited access to organized financial reports. Informal methods may not provide security, reminders, data history, or reliable performance indicators. There is therefore a need for a digital platform that supports structured savings plans, secure transaction tracking, controlled credit access, automated calculations, and a clear financial overview.

2.4 EXISTING SYSTEM

Existing systems in the domain include mobile wallets, microfinance management tools, mobile banking apps, and simple savings trackers. These systems typically offer a subset of the following capabilities:

  1. User registration and login
  2. Wallet balances or account balances
  3. Basic savings entries or transfers
  4. Loan applications or mobile credit facilities
  5. Notification support

However, many of them have limitations such as:

  • Lack of flexible plan-based saving structure
  • Weak transparency between tracked savings and actual savings balance
  • Little support for trial or secret savings plans
  • Minimal financial reporting and analytics
  • Limited customization of security and notification settings
  • Insufficient linkage between savings discipline and loan eligibility

2.5 PROPOSED SYSTEM

The proposed system, Digital Saving Vault (Nzelu Digital Savings), is a cross-platform microfinance savings and credit management application built with Flutter and Django REST Framework. The system enables users to register and authenticate, create savings plans with defined frequencies and goals, make deposits, track withdrawals, simulate or record penalties, view savings reports, manage notifications, and configure preferences.

The system also implements a controlled credit model where users can request loans based on tracked savings, with backend enforcement of eligibility rules. Loan repayments reduce outstanding balances and, when fully completed, trigger interest distribution and reward posting into user savings. Dashboard summaries and financial reports give users greater transparency into their financial activity.

3.2 SYSTEM ARCHITECTURE DIAGRAM

The system architecture shows how the Flutter client communicates with the Django REST API, which then interacts with business logic, the database, and optional external services. The architecture supports separation of concerns, modular development, and future extensibility.

In the client layer, the Flutter application handles the user interface, route navigation, visual analytics, and state management through providers. In the communication layer, HTTP requests are issued through a centralized API service which attaches authentication tokens where required. In the server layer, Django REST Framework handles request routing, serialization, permissions, validation, and response generation. At the persistence layer, the database stores users, savings plans, transactions, loans, repayments, penalties, settings, and notifications. Optional deployment and external layers support production readiness, notifications, and payment integration in future versions.

CHAPTER IV

SYSTEM DEVELOPMENT

4.1 INTRODUCTION

This chapter explains the development process used to implement the Digital Saving Vault system. The project was developed using a modular and iterative approach so that major features could be implemented, tested, and refined incrementally. The technology choice was guided by the need for cross-platform access, secure backend processing, and a maintainable code structure.

4.2 MODULE DESCRIPTION

4.2.1 Authentication and User Profile Module

This module manages user registration, login, token-based session control, profile retrieval, profile settings, and password changes. It forms the entry point to the secure operations of the application.

4.2.2 Savings Plan Management Module

This module allows users to create, view, and manage structured savings plans using daily, weekly, bi-weekly, and monthly frequencies. It also supports secret savings and trial savings plans.

4.2.3 Transaction Processing Module

This module handles deposits, withdrawals, penalty adjustments, and interest reward transactions. It updates linked savings plans and triggers balance recalculation.

4.2.4 Credit and Loan Management Module

This module allows eligible users to request credit, tracks active and completed loans, records repayment transactions, and updates outstanding balances.

4.2.5 Dashboard and Analytics Module

This module aggregates user financial information, including savings balance, tracked savings, active plans, penalties, recent transactions, and financial score, into a single dashboard experience.

4.2.6 Notifications and Alerts Module

This module stores and displays system-generated alerts such as repayment reminders, eligibility notices, savings reminders, and reward notifications.

4.2.7 Settings and Preferences Module

This module gives users control over theme, language, preferred currency, biometric login preference, auto-save options, and notification behavior.

4.2.8 Reports Module

This module generates financial summaries, monthly savings patterns, credit totals, repayment information, and penalty reports for user review.

4.3 METHODOLOGY

The project adopted an Agile-based iterative methodology. This approach was appropriate because it allowed continuous refinement of user interface components, business rules, API endpoints, and report outputs. Development progressed through the following stages:

  1. Requirement Identification: Identifying the need for structured digital savings and controlled credit management.
  2. System Design: Preparing architecture, UML diagrams, data models, and feature flow definitions.
  3. Implementation: Building frontend screens, backend APIs, models, providers, and integration logic.
  4. Testing: Checking authentication, transactions, loans, reports, and settings behavior.
  5. Review and Refinement: Improving usability, correcting logic issues, and updating business rules.
  6. Deployment Preparation: Adding Docker and production-ready backend configuration for future release.

4.4 DEVELOPMENT TOOLS AND ENVIRONMENT

The development environment included Flutter SDK, Dart tooling, Python 3.11, Django, Visual Studio Code or a similar editor, Git version control, and SQLite for local persistence. 4.5 FRONTEND DEVELOPMENT APPROACH

The frontend was implemented as a route-driven Flutter application. The main entry point loads persisted authentication tokens before rendering the widget tree. Providers were used to manage authentication state, savings data, credit data, dashboard state, and theme state. Screens were grouped into authentication, home, savings, loans, reports, notifications, profile, and settings sections. This arrangement helped isolate responsibilities and simplify maintenance.

Modern UI components such as cards, panels, buttons, and visual indicators were used to provide a more engaging financial interface. In particular, the create-plan flow dynamically recalculates suggested saving amounts per day, week, or month depending on the selected target and deadline, thereby making the planning experience interactive and informative.

4.6 BACKEND DEVELOPMENT APPROACH

The backend was implemented as a RESTful API using Django REST Framework. Models defined the domain structure, serializers controlled input/output conversion and validation, and viewsets or function-based endpoints handled operations such as registration, current user access, dashboard summaries, savings management, transaction posting, credit eligibility checking, and financial report generation.

Special attention was given to balance recalculation and business rule enforcement. Instead of relying only on client-side display logic, the backend recomputes savings balance, loan balance, and financial score to ensure consistency regardless of which screen or action triggered the update.

4.7 DATABASE DESIGN STRATEGY

The database design follows a normalized relational structure where user-centered financial records are separated into logical entities. This makes the system easier to query, report on, and maintain. It also ensures that future features such as administrative approval, audit logging, and multi-institution support can be added without redesigning the entire schema.

4.8 BUSINESS RULES IMPLEMENTED

  1. New users receive a default trial savings plan automatically.
  2. Loan eligibility is calculated from tracked savings and active savings plans.
  3. Only one outstanding credit request or active credit is permitted at a time.
  4. Withdrawals are blocked while a user has pending, approved, or active credit.
  5. Fully repaid loans trigger interest distribution and a user savings reward.
  6. Trial plans can be handled separately from normal plans for reporting and restrictions.
  7. Settings are stored at profile level for personalization and future device synchronization.

For example, a deposit affects both the transaction table and the linked savings plan current amount. These paths were examined carefully because errors in financial logic have a greater impact than simple user interface issues.

The credit workflow was also tested closely because it includes restrictions that are important to the integrity of the platform. The system correctly rejected requests above the configured percentage of tracked savings and correctly rejected withdrawals when an active or pending loan existed. These tests confirmed that the backend, rather than the client alone, is responsible for enforcing essential financial rules.

6.2 MODULE IMPLEMENTATION

MODULE 1: USER LOGIN AND AUTHENTICATION

Authentication was implemented using Django user management and JWT-based API authentication. The Flutter client loads stored tokens during startup and uses authenticated API requests to retrieve protected resources.

MODULE 2: SAVINGS PLAN MANAGEMENT

Users can create normal, secret, and trial savings plans. Each plan includes title, frequency, duration, goal amount, amount per period, grace period, and penalty policy. The backend stores plan records and calculates progress toward savings goals.

MODULE 3: TRANSACTION PROCESSING

The transaction module records deposits, withdrawals, penalties, and interest rewards. Each transaction is linked to a user and optionally to a savings plan. Deposits increase plan current amounts, while withdrawals and penalties reduce them where applicable.

MODULE 4: CREDIT AND LOAN MANAGEMENT

Credit requests are processed using backend rules that compare the requested amount against tracked savings. The system allows only one outstanding credit request or active credit at a time. Repayment updates remaining balances and changes loan status when the balance reaches zero.

MODULE 5: DASHBOARD AND ANALYTICS

A dashboard summary endpoint returns user details, balances, active plans, credit status, unread notifications, penalties, and recent transactions in a single API call. This reduces client round-trips and keeps the UI synchronized.

MODULE 6: NOTIFICATIONS

Notifications are stored per user and may represent reminders, missed savings, penalty actions, loan approval, repayment notices, and interest rewards. Users can mark single notifications or all notifications as read.

MODULE 7: SETTINGS

User settings include theme, language, currency, notification toggles, biometric preference, two-factor preference, payment methods, feedback, and default savings plan references.

MODULE 8: REPORTS

The reports module calculates monthly savings, total credit taken, total repaid, total penalties, financial score, and savings balances for display in report screens.

CHAPTER VII

PROBLEMS FACED AND SOLUTIONS

7.1 INTRODUCTION

During the development of Digital Saving Vault, several technical and design challenges were encountered. These issues were related to data synchronization, business rule enforcement, credit workflow consistency, state management, and user interface organization. This chapter outlines the major problems and the solutions applied.

7.2 PROBLEMS FACED

Balance Synchronization Complexity: Savings balances had to remain accurate while transactions, interest rewards, penalties, and withdrawals affected totals in different ways.

Tracked Savings versus Actual Savings: The system needed to distinguish between tracked plan totals and recalculated savings balances to support correct reporting.

Credit Restriction Logic: Loan requests needed strict validation so users could not exceed eligibility thresholds or hold multiple outstanding credits.

Repayment and Reward Distribution: Loan repayment completion had to trigger status changes, interest distribution, and a reward transaction back into user savings.

Frontend Refresh State: Multiple screens depended on shared financial data, which required careful provider-based synchronization after transactions or repayments.

Settings Persistence: User preferences needed to persist reliably across sessions and still remain aligned with backend profile settings.

7.3 SOLUTIONS

Backend Recalculation Methods: Dedicated profile methods were implemented to recalculate savings balance, loan balance, and financial score whenever key actions occur.

Centralized Dashboard Summary Endpoint: A single summary endpoint was implemented to reduce repeated network calls and keep the client state consistent.

Strict Loan Validation: Backend checks were added to ensure requested credit does not exceed the allowed percentage of tracked savings and that only one outstanding credit is allowed.

Automated Interest Distribution: Loan completion logic creates interest distribution records, updates savings, and sends a notification automatically.

Provider-Based Refresh: Flutter providers reload plan, transaction, and loan data when users navigate across key sections of the app.

Flexible Settings Payload: Profile settings were grouped into a dedicated payload structure for easier persistence and retrieval.

7.4 LESSONS LEARNED

One of the major lessons learned from this project is that financial applications require much stronger consistency guarantees than ordinary CRUD applications. A simple mistake in how balances are updated or how repayments are tracked can produce incorrect financial outputs, which reduces trust immediately. This reinforced the value of putting core calculations on the backend rather than relying solely on client-side assumptions.

Another lesson is that a visually attractive frontend is not enough on its own. Financial users benefit most when presentation is paired with clear rules, understandable reports, and guided workflows. The plan-creation screen, for example, became more effective after it started translating targets and deadlines into per-day, per-week, or per-month guidance.

The project also showed the importance of modular architecture. Because providers, screens, models, serializers, and viewsets were separated by responsibility, it was easier to refine one area of the system without rewriting unrelated sections. This will be especially valuable in future expansion phases.
